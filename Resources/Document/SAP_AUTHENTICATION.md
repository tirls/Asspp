# Native authentication matched to AssppWeb

This branch starts from official Asspp commit
`caed708182c61897bd539557a10618f9b0eba066`. It changes authentication and
account refresh, retaining upstream catalog, purchase, download, version and
IPA processing code. It has no WKWebView, Wisp or Cloudflare dependency.

The reference is the AssppWeb SAP implementation at `835a54d`, whose login
flow succeeded in the local diagnostic browser on 2026-09-30. Browser success
does not establish native iOS compatibility; the final test is on a device.

## Protocol alignment

- Encode the 12-character device identifier as UTF-8, as Web's TextEncoder does.
  Do not hex-decode it into six bytes.
- Resolve the real CommerceCore `_get_mac_address` export. Do not substitute
  a function returning the supplied identifier as a MAC address.
- Send attempt `4` without a verification code and `2` with one.
- Serialize the login plist in the same order and format as the Web engine.
  Sign and send exactly those bytes on redirects and bounded transient retries.
- Use the same Configurator user agent and login content type as Web.
- Normalize Apple's native authentication URLs to `/auth/v1/native/fast/`,
  preserving query fields while setting one guid. Both the native host and
  legacy buy/pod hosts are validated before credentials are sent.
- Retain the signer and private cookie jar through the verification-code
  challenge; release the pending session on success, other errors, account
  changes or dismissal of the add-account form.
- Normalize Foundation domain cookies when handing them to ApplePackage.

One native authenticator cannot run simultaneous signing exchanges. Sessions
are isolated by account, and refresh starts a new independent authenticator.
The original global device identifier and Keychain account schema are retained.

## Build and checks

GitHub Actions runs `Resources/Scripts/check.sap.sh` and
`Resources/Scripts/build.unsigned.ios.sh` on macOS. The workflow emits an unsigned
IPA and SHA-256 checksum. No Docker or local Windows Xcode installation is needed.

The pinned Unicorn interpreter uses TCI without JIT. Build inputs are verified;
Apple SAP data is compressed as `.sapz` and checked after decompression at runtime.
Existing source and license notices are preserved in the IPA.

The checks compare native serialized request bytes with
`Resources/Tests/WebLoginBody.xml`, generated by the actual Web plist builder.
They also check cookie handling, manual redirects, error classification, resource
packing, the native interpreter and the public certificate/setup handshake with
12-character hardware input. No account credentials are used by CI.

Passing these checks does not prove Apple accepts a login. Native requests still
use Foundation URLSession and the phone's network, while Web uses libcurl/Mbed TLS
over Wisp and a server network. If device login fails, those are the next variables
to investigate, without attributing HTML/empty responses to an incorrect password.
